# 拉密小游戏 · 多人联机方案

## 0. 结论先行

| 问题 | 答案 |
| --- | --- |
| 是不是先做登录？ | **是。** 没有 openid 就没法区分玩家，房间、对局、战绩全都无从谈起 |
| 必须用云开发吗？ | **不是必须，但它是最省事的选择**（不用买服务器、不用配域名备案） |
| 我的项目一开始不是用云开发建的，能用吗？ | **能。云开发是"后加"的**，三步就能接上，现有代码一行都不用改 |

---

## 1. 云开发怎么接入（重点）

### 1.1 云开发不是"项目类型"

很多人的误解是"建项目时要选云开发模板"。实际上**云开发是独立于项目类型的一个能力**：小程序、小游戏、插件都能后加，跟当初建项目时选什么完全没有关系。

你现在这个项目（小游戏，`compileType: "game"`）直接就能接。

### 1.2 三步接入

#### 第 1 步：开通环境，拿到环境 ID

1. 微信开发者工具 → 顶部工具栏点 **「云开发」** 按钮
2. 首次点击会引导开通 → 同意协议 → **创建环境**
3. 环境名随便起（比如 `rammi-prod`），创建完在控制台左上角能看到一个 **环境 ID**，形如：

```
rammi-prod-8g9k2x
```

**把这个 ID 记下来，后面要写进代码。**

> 个人主体也能开通，有免费额度。云开发是**按量计费**，开发阶段基本用不到付费额度。

#### 第 2 步：告诉开发者工具"云函数放在哪"

在 [project.config.json](../project.config.json) 里加一行：

```json
{
  "cloudfunctionRoot": "cloudfunctions/",
  ...
}
```

加完之后，项目根目录会自动出现一个**带云朵图标的 `cloudfunctions` 文件夹**。以后每个云函数就是这个文件夹下的一个子目录。

#### 第 3 步：客户端初始化

在 [js/main.js](../js/main.js) 的最前面加：

```js
if (wx.cloud) {
  wx.cloud.init({
    env: 'rammi-prod-8g9k2x',   // ← 换成你的环境 ID
    traceUser: true,
  });
  console.log('[cloud] 初始化完成');
} else {
  console.error('[cloud] 当前基础库不支持云开发，请升级到 2.2.3 以上');
}
```

**环境 ID 建议集中放在一个常量文件里**，不要到处硬编码：

```js
// js/net/config.js
module.exports = { ENV_ID: 'rammi-prod-8g9k2x' };
```

### 1.3 注意事项

| 事项 | 说明 |
| --- | --- |
| 基础库版本 | 小游戏支持 `wx.cloud`，但要求 **基础库 ≥ 2.2.3**。检查 `project.private.config.json` 里的 `libVersion` |
| 不需要 appid/secret | 云函数里 `cloud.getWXContext().OPENID` 是**微信平台保证的**，不用自己做 `code2Session`，也不会有密钥泄漏风险 |
| 数据库权限 | **建议全部设成「仅管理端可读写」**，所有读写都走云函数。这样客户端绕不过去，天然防作弊 |
| 多个环境 | 可以建 `dev` / `prod` 两个环境，开发时切 `dev`，上线切 `prod` |
| 计费 | 云函数调用次数 + 数据库读写次数 + 存储 + 实时推送连接数。回合制游戏量很小，但**轮询频率别设太高** |

## 2. 整体架构

### 2.1 核心原则：服务器权威

```
现在（单机）：
   点「出牌」→ 客户端自己校验 → 改本地 game → 画出来

联网后：
   点「出牌」→ 把"意图"发给云函数 → 云函数校验 → 写库 → 广播 → 客户端照着重画
```

**为什么必须这样**：客户端代码用户完全可控。判定放客户端，改一行就能随便出牌、看穿对手手牌。

**我们有个很有利的条件**：`js/core/` 完全不依赖 `wx`，能在 Node 里直接跑 —— **可以原封不动放进云函数**。同一份规则，客户端和服务端共用。

### 2.2 架构图

```
┌─ 客户端 ───────────────┐        ┌─ 云开发 ──────────────────┐
│  wx.cloud.init          │        │                           │
│     ↓                   │        │  【login 云函数】          │
│  callFunction('login')  │ ─────→ │    OPENID → users 集合     │
│     ↓ openid + 昵称头像  │ ←───── │                           │
│                         │        │                           │
│  建房 / 加入 / 同步      │        │  【action 云函数】         │
│  摸牌 / 出牌             │ ─────→ │    ① 验身份（在座吗）      │
│     ↓                   │        │    ② 验版本（乐观锁）      │
│  渲染服务器给的状态       │ ←───── │    ③ 超时懒判定            │
│                         │        │    ④ js/core 校验动作      │
│                         │        │    ⑤ 写回 rooms            │
│  watch(rooms[roomId])   │ ═════→ │  rooms 集合变更 → 实时推送  │
└─────────────────────────┘        └───────────────────────────┘
```

## 3. 数据库设计

云开发数据库是文档型（类似 MongoDB），在控制台建三个集合。

### 3.1 `users` —— 用户

```js
{
  _id: 'oXXXXXX...',        // 直接用 openid 当主键，天然唯一
  nickname: '老张',
  avatar: 'cloud://...',     // 头像 fileID（上传到云存储后得到）
  createdAt: 1728000000000,
  updatedAt: 1728000000000,
  stats: { games: 0, wins: 0 }   // 可选，做战绩
}
```

> 昵称头像**不能静默获取**，要用「头像昵称填写能力」：用户点头像/昵称按钮，自己选。所以流程是"静默拿 openid → 首次进入让用户填一次"。

### 3.2 `rooms` —— 房间 + 对局状态

```js
{
  _id: 'R8K3Q2',            // 6 位房间号，生成时检查不重复
  version: 42,              // 乐观锁版本号，每次状态变化 +1
  status: 'waiting',        // 'waiting' | 'playing' | 'over'
  ownerOpenid: 'oXXXXXX...',
  maxPlayers: 2,            // 2~4

  seats: [
    {
      openid: 'oXXXXXX...',
      nickname: '老张',
      avatar: 'cloud://...',
      lastSeenAt: 1728000000000,   // 心跳时间，用来判断掉线
      online: true,
    },
  ],

  game: null,               // status 变成 playing 后才有值，见 3.3
  lastActionAt: 1728000000000,  // 最近一次动作时间，用于超时懒判定

  createdAt: 1728000000000,
  updatedAt: 1728000000000,
}
```

**座位顺序就是玩家编号**：`seats[0]` 是 0 号位，`seats[1]` 是 1 号位。这样 `seats.length` 直接就是 `RummyGame` 需要的 `playerCount`。

### 3.3 `rooms.game` —— 对局状态（RummyGame 的序列化）

```js
game: {
  playerCount: 2,
  current: 0,
  turnState: 'await-draw',
  turnPlacedValue: 0,
  consecutivePasses: 0,
  winner: null,
  _meldSeq: 3,
  players: [ { index: 0, isHuman: true, hand: [tile...], hasMelded: false }, ... ],
  pool: [tile...],
  table: [ { id: 'm0', owner: 0, tiles: [tile...] }, ... ],
}
```

`tile` 就是现在的结构 `{ id, color, number, isJoker }`，纯数据，可以直接 JSON 化。

**一副牌大约 6KB JSON**，一局完整状态不到 10KB，完全在单文档限制内（云开发单文档上限 16MB）。

> 进阶做法：只存"动作日志"，用重放还原状态。好处是有回放、能审计，但复杂度高一截。**第一版建议直接存完整状态。**

### 3.4 `moves` —— 动作日志（可选）

```js
{
  _id: 自动,
  roomId: 'R8K3Q2',
  seq: 17,                  // 第几步
  seat: 1,
  type: 'draw',             // 'draw' | 'play' | 'timeout' | 'endTurn'
  payload: null,
  createdAt: 1728000000000,
}
```

**不参与游戏逻辑，只用来做战绩和排查"这局到底谁作弊了"**。第一版可以先不做。

## 4. 云函数接口设计

只做**两个**云函数，别建一堆。

### 4.1 `login` —— 登录

```
调用：callFunction({ name: 'login', data: {} })

云函数逻辑：
  const { OPENID } = cloud.getWXContext();     // 微信保证可信
  const user = await db.collection('users').doc(OPENID).get();  // 不存在会抛错
  if (不存在) → 创建一条 users 记录
  return { openid: OPENID, nickname, avatar, isNew: true/false }
```

**客户端不需要传任何凭证** —— 云函数天然知道你是谁，这就是云开发最大的便利。

### 4.2 `action` —— 所有房间/对局操作

统一入口，用 `type` 区分：

```
调用：callFunction({ name: 'action', data: { type, roomId, version, payload } })
返回：{ ok: true, version, view }  或  { ok: false, error: '中文提示' }
```

| type | 入参 | 作用 |
| --- | --- | --- |
| `updateProfile` | `{ nickname, avatar }` | 存昵称头像 |
| `createRoom` | `{ maxPlayers }` | 开新房，返回 roomId |
| `joinRoom` | `{ roomId }` | 加入房间 |
| `leaveRoom` | `{ roomId }` | 离开（waiting 时直接移除座位） |
| `start` | `{ roomId, version }` | 房主开局，初始化 game |
| `sync` | `{ roomId }` | **拉一次最新状态**（轮询兜底 & 断线重连） |
| `ping` | `{ roomId }` | 心跳，更新 lastSeenAt |
| `draw` | `{ roomId, version }` | 摸牌 |
| `play` | `{ roomId, version, payload: { table } }` | 出牌 |

### 4.3 `action` 的通用校验流程

**每个动作都走这 9 步**，这是整个方案的核心：

```js
async function action(event) {
  const { OPENID } = cloud.getWXContext();
  const { type, roomId, version, payload } = event;

  // ① 拉房间
  const room = await db.collection('rooms').doc(roomId).get();
  if (!room) return fail('房间不存在');

  // ② 验身份：我在座吗？坐哪？
  const seat = room.seats.findIndex((s) => s.openid === OPENID);
  if (seat < 0) return fail('你不在这个房间里');

  // ③ 验版本：客户端看到的版本和我一致吗？（乐观锁）
  if (logRoom.version !== version) return fail('状态已更新，请重新同步');

  // ④ 超时懒判定：上一个动作超过 60 秒就替他摸牌
  settleTimeout(room);

  // ⑤ 还原对局
  const game = RummyGame.fromJSON(room.game);

  // ⑥ 执行业务校验（复用 js/core，抛异常就是非法）
  try {
    if (type === 'draw') game.draw(seat);
    else if (type === 'play') game.submitMove(seat, payload.table);
    else if (type === 'start') { ... }
  } catch (err) {
    return fail(err.message);          // 直接把中文提示回给客户端
  }

  // ⑦ 乐观锁写回：只有 version 没变才更新成功
  const res = await db.collection('rooms')
    .where({ _id: roomId, version })
    .update({ data: {
      game: game.toJSON(),
      version: version + 1,
      lastActionAt: Date.now(),
      updatedAt: Date.now(),
    }});
  if (res.stats.updated === 0) return fail('状态已更新，请重新同步');  // 被别人抢先了

  // ⑧ 返回"按座位过滤"的视图 —— 关键！
  return ok({ version: version + 1, view: viewFor(game, seat, room) });
}
```

### 4.4 ⚠️ 手牌过滤（最容易犯的致命错误）

**绝对不能把所有人的手牌都发给客户端**，否则改个抓包就能看穿底牌。

```js
function viewFor(game, seat, room) {
  return {
    version, status, current: game.current, turnState: game.turnState,
    poolCount: game.pool.length,
    table: game.table,                       // 桌面是公开信息
    you: seat,
    timeLeft: Math.max(0, TURN_LIMIT - (Date.now() - room.lastActionAt) / 1000),
    players: game.players.map((p) => ({
      index: p.index,
      hasMelded: p.hasMelded,
      handCount: p.hand.length,
      hand: p.index === seat ? p.hand : null,   // ← 别人的只给张数，不给牌面
    })),
  };
}
```

### 4.5 超时懒判定

**60 秒回合计时必须在服务端**（客户端计时可以被改，还要解决"有人掉线卡住全场"）。

不用真开定时器，用**懒判定**：任何请求进来时先检查一次。

```js
function settleTimeout(room) {
  if (!room.game) return false;
  if (Date.now() - room.lastActionAt < TURN_LIMIT * 1000) return false;

  const game = RummyGame.fromJSON(room.game);
  const who = game.current;
  game.draw(who);            // 自动摸牌
  if (game.turnState !== 'over') game.endTurn(who);
  room.game = game.toJSON();
  room.lastActionAt = Date.now();
  return true;
}
```

**好处**：即使全场都没人动，下一个人一操作就会把超时补上，永远不会卡死。

## 5. 客户端模块设计

```
js/net/
├── config.js    环境 ID 等常量
├── cloud.js     wx.cloud.init + callFunction 统一封装（超时、重试、错误码）
├── session.js   登录态：openid / 昵称 / 头像，缓存在 wx.setStorageSync
├── room.js      建房 / 加入 / 同步 / 心跳
├── action.js    摸牌 / 出牌
└── view.js      把服务器 view 转成渲染层认识的 game 形状
```

### 5.1 `cloud.js` —— 统一封装

```js
function call(name, data) {
  return new Promise((resolve, reject) => {
    wx.cloud.callFunction({
      name,
      data,
      success: (res) => resolve(res.result),
      fail: (err) => reject(new Error(mapError(err))),
    });
  });
}
```

**统一加上超时和重试**：网络抖动很常见，但要区分"可以重试"（超时）和"不能重试"（业务拒绝）。

### 5.2 `view.js` —— 让旧渲染代码能复用

渲染层现在读的是 `game.players[i].hand`、`game.table`、`game.pool.length`。服务器给的是 `handCount`，所以要适配一层：

```js
function viewToGame(view) {
  return {
    current: view.current,
    turnState: view.turnState,
    turnPlacedValue: view.turnPlacedValue,
    pool: { length: view.poolCount },
    table: view.table,
    players: view.players.map((p) => ({
      index: p.index,
      isHuman: p.index === view.you,
      hasMelded: p.hasMelded,
      hand: p.hand || [],
      handCount: p.handCount,
    })),
  };
}
```

**需要跟着改一处**：`game-renderer.js` 里画对手手牌张数用的是 `p.hand.length`，要改成 `p.handCount`（拿不到时回退到 `p.hand.length`）。

### 5.3 `GameScene` 的改造

**改动最集中的是 `_onButton`**：从"本地改 game"变成"发意图 → 等响应 → 应用服务器状态"。

```js
async _onButton(id) {
  if (this.busy) return;          // 防连点
  this.busy = true;
  this.message = '提交中…';

  try {
    const res = await action.send(id, {
      roomId: this.roomId,
      version: this.version,
      payload: id === 'play' ? { table: draftUtil.groupIds(this.draft) } : null,
    });

    if (!res.ok) {
      this.message = res.error;   // 服务器拒绝 → 保留摆放让玩家修改
      return;
    }
    this.applyView(res.view);     // 应用服务器返回的新状态
  } catch (err) {
    this.message = '网络异常，请重试';
  } finally {
    this.busy = false;
  }
}
```

### 5.4 拖动可以完全留在本地

**这是好消息**：之前做的 `game` / `draft` 两层设计，正好对应联网后的分工。

| | 联网后 |
| --- | --- |
| `game` | 变成"服务器同步下来的只读状态" |
| `draft` | **保持在本地**，拖动改它，手感完全不受网络影响 |
| 「出牌」 | 才把 `draft.table` 发给服务器 |

所以拖拽体验一点都不受影响，只有点按钮那一刻才等一次响应。

## 6. 关键流程时序

### 6.1 登录

```
启动 → wx.cloud.init
     → callFunction('login')            （不带任何凭证）
     → 云函数读 getWXContext().OPENID
     → 查 users，没有就创建
     → 返回 { openid, nickname, avatar }
     → 客户端存 session，进入首页
     → 如果 nickname 为空 → 弹「填写昵称头像」
```

### 6.2 建房 / 加入

```
房主：createRoom({ maxPlayers: 2 })
      → 云函数生成不重复的 6 位房间号，写入 rooms，status='waiting'
      → 返回 roomId
      → 客户端 wx.shareAppMessage({ query: 'roomId=R8K3Q2' })

好友：点分享卡片进入
      → onShow 的 query 里带 roomId
      → joinRoom({ roomId })
      → 云函数检查：房间存在？没满？没在打？
      → 把 openid 加进 seats
      → 全员 watch 到变更，界面更新

房主点「开始」
      → start({ roomId, version })
      → 云函数 new RummyGame({ playerCount: seats.length }) → toJSON 存进 room.game
      → status='playing'
```

### 6.3 出牌

```
玩家拖动（本地 draft，不联网）
  ↓
点「出牌」
  ↓
callFunction('action', { type:'play', roomId, version, payload:{ table } })
  ↓
云函数：验身份 → 验版本 → 超时判定 → submitMove 校验
  ├─ 失败 → 返回 { ok:false, error:'有一组牌不合法' }  → 客户端保留摆放
  └─ 成功 → 乐观锁写库 → 返回 { ok:true, version, view }
  ↓
所有客户端 watch 到 rooms 变更（或请求方直接用返回的 view）
  ↓
各自重画：桌面多了一组牌，对手手牌数减了几张
```

### 6.4 断线重连

```
玩家重进游戏
  → 用 openid 查 rooms（where seats.openid == 我 and status != 'over'）
  → 找到房间 → sync({ roomId })
  → 拿到最新 view → 继续玩
```

同时每个客户端每 10 秒 `ping` 一次；云函数更新 `seats[i].lastSeenAt`。超过 30 秒没更新，界面上给那个座位标「掉线中」。

## 7. 安全与反作弊

| 措施 | 说明 |
| --- | --- |
| **手牌按座位过滤** | 最重要的一条。只给请求者自己的手牌 |
| 一切判定在服务端 | 客户端只发意图，改客户端改不了结果 |
| 身份来自 `getWXContext` | 不用信客户端传的任何 id |
| 座位校验 | 每个人只能操作自己的座位 |
| 版本乐观锁 | 防止并发覆盖 |
| 数据库权限设「仅管理端」 | 客户端不能直接读写 |
| 动作日志（可选） | 出问题时能复盘 |

### 8.1 `toJSON` / `fromJSON` 怎么写

```js
// js/core/game.js
toJSON() {
  return {
    playerCount: this.playerCount,
    current: this.current,
    turnState: this.turnState,
    turnPlacedValue: this.turnPlacedValue,
    consecutivePasses: this.consecutivePasses,
    winner: this.winner,
    _meldSeq: this._meldSeq,
    players: this.players,
    pool: this.pool,
    table: this.table,
  };
}

static fromJSON(data) {
  const g = Object.create(RummyGame.prototype);  // 不走构造函数，避免重新发牌
  Object.assign(g, data);
  return g;
}
```

**这部分单机也能受益**：做完就有了存档功能（退出再进来能接着打）。

## 9. 分阶段实施

| 阶段 | 做什么 | 验收标准 | 影响单机吗 |
| --- | --- | --- | --- |
| **1** | 开通云开发环境、加 `cloudfunctionRoot`、`wx.cloud.init`、写 `login` 云函数 | 控制台能打出自己的 openid | 不影响 |
| **2** | `users` 集合 + 昵称头像填写 + 登录场景 | 昵称头像能存能读，重启还在 | 不影响 |
| **3** | `rooms` 集合 + `createRoom`/`joinRoom`/`sync` + 房间场景 + 好友邀请 | 两台设备能进同一房间，看到对方 | 不影响 |
| **4** | `action` 云函数 + `toJSON/fromJSON` + `viewFor` + `GameScene` 改造 | 两个人能轮流摸牌出牌，改客户端改不了结果 | 单机保留为"练习模式" |
| **5** | `watch` 实时推送 + `ping` 心跳 + 服务端超时 + 断线重连 + 结算 | 杀掉一个人，另一个能继续玩 | — |
| **6** | 匹配队列、排行榜、战绩 | — | — |

**阶段 1~3 完全不碰对局逻辑**，单机玩法一点不受影响，可以先跑通"两个人进同一个房间"。

**阶段 4 是关键**，不要往后拖。如果先做"客户端判定 + 服务器只转发"，后面再改成服务器权威，等于把客户端逻辑重写一遍。

## 10. 常见坑

| 坑 | 后果 | 对策 |
| --- | --- | --- |
| 手牌全量下发 | 抓包就能看穿对手底牌 | `viewFor` 按座位过滤 |
| 每帧写数据库 | 配额几秒打满 | 只同步"动作"，不同步拖动 |
| 用客户端计时做超时 | 可被篡改；掉线的人卡住全场 | 超时懒判定放云函数 |
| `js/core` 两份代码不同步 | 服务端和客户端判定不一致，诡异 bug | 写个同步脚本，或做成独立目录 |
| 昵称头像静默获取 | 微信不允许，会失败 | 用「头像昵称填写能力」按钮 |
| 轮询频率太高 | 配额消耗快 | 1~2 秒一次足够，回合制不需要更密 |
| 没做防连点 | 一次点击发出两个请求 | 客户端 `busy` 标志 + 服务端版本锁 |

## 11. 关于"实时看对手拖动"

这个需求单独说明一下，因为它有个隐蔽的陷阱。

**技术上做得到**，但**手牌不能同步**：

```
桌面已有的牌是公开信息 → 同步没问题
手牌是私有信息        → 一旦同步，游戏的核心策略就没了
```

具体例子：桌上有 红11 红12 红13，对手手里有 红10。如果他拖出来接顺子没接上又放回去，你通过实时拖动流就知道"他手里有红10"。

**所以第一版的做法是**：只同步"动作"（摸牌 / 出牌），配上本地的动画把它做得像实时：

| 做什么 | 效果 | 需要联网吗 |
| --- | --- | --- |
| 对手头像旁显示「思考中…」 | 知道他还在 | 一个字段 |
| 出牌时牌从手牌飞向桌面的动画 | 观感提升最大 | 不需要，纯本地 |
| 刚放下的牌高亮 2 秒 | 一眼看到重点 | 不需要 |
| 对手回合的 60 秒倒计时 | 有紧张感 | 服务器给 timeLeft |

如果以后确实要做"桌面拖动 + 手牌翻面（只显示牌背）"的逐帧同步，那才需要**自建 WebSocket 服务器**（内存转发、不落库），因为云开发的实时推送是数据库变更驱动的，扛不住每秒几十条位置消息。
