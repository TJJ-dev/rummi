# 拉密（Rummikub）微信小游戏 — 技术方案

| 项目 | 说明 |
| --- | --- |
| 项目名 | rammi-game |
| 形态 | 微信小游戏（canvas 2D，`compileType: "game"`） |
| 语言 | JavaScript（CommonJS），无构建、无第三方依赖 |
| 当前版本 | 0.3.0 |

---

## 1. 项目概述

### 1.1 目标

在微信小游戏里实现一局完整可玩的拉密（Rummikub）：4 色数字牌 + 百搭，凑顺子与刻子，先出完手牌者获胜。

当前支持 2~4 人对局，1 名真人 + 若干电脑。

### 1.2 产品形态

**是微信小游戏，不是页面式小程序。** 两者在微信里是并列的两种形态，同一个目录不能同时是两者：

| | 小游戏（本项目） | 小程序 |
| --- | --- | --- |
| 入口 | `game.js` + `game.json` | `app.js` + `app.json` |
| 界面 | canvas 手绘 | WXML + WXSS |
| 项目类型 | `compileType: "game"` | `compileType: "miniprogram"` |

注意：切换形态后开发者工具会缓存旧的项目类型，需要在工具里重新导入项目才能生效。

### 1.3 当前完成度

已实现：

- 106 张牌堆、洗牌、轮流发牌
- 顺子 / 刻子的合法性判定（含百搭代替）
- 首次出牌 ≥ 30 分限制
- 自由拖拽出牌：拖到空地新建一组，拖到已有牌组自动紧贴吸附
- 重排桌面已有牌组
- 回合流转、电脑 AI、两种胜利判定
- 首页 / 模式选择 / 对局三个场景
- 23 项纯逻辑单元测试 + 无界面对局模拟器

待实现：

- 百搭的挪动与替换（以及"百搭代表了哪个数字"的记录）
- 整组拖动
- 更强的 AI
- 联网对战

## 2. 技术选型

### 2.1 运行形态

微信小游戏只提供一个全屏 canvas，没有 DOM、没有 WXML、没有页面栈。所有界面元素（按钮、面板、文字）都要自己画，点击命中要自己算。

渲染循环用 `requestAnimationFrame`，输入只有 `wx.onTouchStart / onTouchMove / onTouchEnd` 三个触摸事件。

### 2.2 模块规范

统一使用 CommonJS（`require` / `module.exports`）。原因：

1. 微信小游戏的编译器原生支持；
2. 同一份代码可以直接在 Node 里 `require` 运行，**不需要任何构建或转译**——这是下一条决策的前提。

### 2.3 关键决策：核心逻辑与平台解耦

**`js/core/` 目录下不出现任何 `wx.*` 调用。**

带来三个直接收益：

1. **可测试**：规则代码能在 Node 里直接跑单元测试，不需要开发者工具。
2. **可复用**：以后做联网对战时，同一份 `js/core/` 可以直接放到云函数里做服务端裁定。
3. **可换壳**：如果以后要改成页面式小程序，只需要重写界面层。

`wx.*` 只出现在 `js/main.js` 一个文件里，它负责把平台事件翻译成朴素的 `(x, y)` 坐标，再往下传。

### 3.3 依赖方向

依赖是**单向**的，不会出现循环引用：

```
main.js → app.js → 各 Scene → game-scene.js
                                  │
              ┌───────────────────┼───────────────────┐
              ▼                   ▼                   ▼
        board-layout.js      game-input.js      board-draft.js
              ▲                   │                   │
              └──── game-renderer.js ────────────────┘
                                  │
                                  ▼
                             js/core/*
```

约定：

- `board-layout.js` 不依赖任何人，是最底层；
- 三个纯函数模块之间不互相依赖；
- **场景之间不互相 `require`**，切换一律通过 `this.app` 的方法。

### 3.4 主循环与事件流

`js/main.js` 是唯一的平台入口：

```js
const app = new App({ ctx, width: W, height: H });   // main.js:24

let last = Date.now();
function loop() {                                    // main.js:47
  const now = Date.now();
  const dt = Math.min(0.1, (now - last) / 1000);     // 秒，封顶 0.1 防跳帧
  last = now;
  app.update(dt);
  app.render();
  requestAnimationFrame(loop);
}
```

事件流：

```
wx.onTouchStart/Move/End
   → main.js 取 touches[0] 或 changedTouches[0] 的 clientX/clientY
   → app.onTouchXxx(x, y)
   → 当前场景的 onTouchXxx(x, y)
```

**渲染是全量重绘**：每一帧清屏、重画所有内容。所以改数据就等于刷新界面，不需要"通知视图更新"。

### 4.2 牌 tile

`core/tiles.js:25`

```js
function makeTile(color, number) {
  return { id: `t${_seq++}`, color, number, isJoker: false };
}
function makeJoker() {                                   // tiles.js:29
  return { id: `j${_seq++}`, color: 'joker', number: 0, isJoker: true };
}
```

一张普通牌：

```js
{ id: 't37', color: 'red', number: 5, isJoker: false }
```

一张百搭：

```js
{ id: 'j0', color: 'joker', number: 0, isJoker: true }
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 全局唯一。普通牌 `t0..t103`，百搭 `j0..j1` |
| `color` | string | `'red'` / `'orange'` / `'blue'` / `'black'` / `'joker'` |
| `number` | number | `1~13`；**百搭固定为 0（哨兵值）** |
| `isJoker` | boolean | 是否百搭。**判断百搭一律看这个字段，不要看 number** |

#### 为什么 id 是必需的

整副牌里"红5"有两张，光靠 `color + number` 无法区分"我手里的红5"和桌上那张。选中、拖动、去重、比较全都依赖 `id`。

#### 百搭 number = 0 的注意事项

`number = 0` 只是占位。所有"取点数"的地方都必须先判断 `isJoker`：

| 场景 | 代码位置 | 处理方式 |
| --- | --- | --- |
| 计分 | `tiles.js:61` `tileValue` | 百搭算 **30 分**，不是 0 分 |
| 首出点数 | `rules.js:74` `meldValue` | 用 `realTiles()` 过滤，百搭**不计入** |
| 渲染 | `widgets.js:45` `drawTile` | 百搭画 `★`，不画 number |
| 顺子/刻子判定 | `rules.js:17` `realTiles` | 先排除百搭，再看非百搭牌的连续性与空位 |
| 手牌排序 | `tiles.js:70` `sortHand` | 先按 `isJoker` 排，百搭放最后 |

**已知限制**：百搭"替代成了哪个数字"目前没有被记录。`isRun` / `isGroup` 是每次现算的，算完结果即丢。因此现在能判断"把百搭当红6用，这组合法"，但说不出"这个百搭代表红6"。若要在界面上标注，需要给 tile 增加 `represents` 字段。

### 4.3 对局 RummyGame

`core/game.js:27`

```js
{
  playerCount: 4,
  players: [
    { index: 0, isHuman: true, hand: [tile, ...], hasMelded: false },
  ],
  pool: [tile, ...],                          // 牌堆，摸牌 = pool.pop()
  table: [                                    // 桌面牌组
    { id: 'm0', owner: 0, tiles: [tile, tile, tile] },
  ],
  current: 0,                                 // 轮到谁
  turnState: 'await-draw',                    // 'await-draw' | 'await-play' | 'over'
  turnPlacedValue: 0,                         // 本回合已出的点数（首出 30 分判定用）
  consecutivePasses: 0,                       // 连续过牌次数（牌堆摸空后结算用）
  winner: null,
  log: [],
  _meldSeq: 0,
}
```

这是**唯一的权威状态**，只能通过 4 个方法修改：

| 方法 | 作用 | 谁调用 |
| --- | --- | --- |
| `draw(index)` | 摸一张牌 | 玩家点「摸牌」/ AI |
| `playMeld(index, ids)` | 打出一组全新的牌组 | **电脑 AI** |
| `submitMove(index, tableMelds)` | 提交整张桌面的新摆法 | **玩家拖牌** |
| `endTurn(index)` | 结束回合，轮到下一位 | 两边都会调 |

### 4.4 草稿 draft

`ui/game/board-draft.js`

```js
{
  hand: ['t3', 't17'],                        // 手牌：只有 id，顺序 = 显示顺序
  table: [                                    // 桌面：带坐标的"组"
    { x: 115, y: 155, ids: ['t1', 't2'] },    // 第 1 组，锚点在左上角
    { x: 275, y: 255, ids: ['t5'] },          // 第 2 组
  ],
}
```

**这是本项目最核心的设计。** 草稿是"玩家正在编辑、还没提交的副本"，拖动只改它，点「出牌」时才通过 `submitMove` 交回 `game`。

为什么需要它：

1. **中间状态是非法的**：摆牌过程中桌面可能短暂地不合法（缺一张的顺子），这是必经状态。
2. **校验失败要能回滚**：玩家摆了 5 分钟，提交失败时不能把桌面清空。
3. **要能撤销**：重新调一次 `_syncDraft()` 就从 `game` 还原。

**位置设计的关键**：

| 概念 | 存在哪 | 特点 |
| --- | --- | --- |
| 组的位置 | `group.x` / `group.y` | **数据**，玩家拖到哪就是哪，完全自由 |
| 组内的顺序 | `group.ids` 数组顺序 | 由落点相对已有牌在左半边还是右半边决定 |
| 组内每张牌的坐标 | **不存**，渲染时算出来 | `x = group.x + i × (牌宽 + 2)` |

因为组内间距是常量、顺序是确定的，**组内永远不会重叠**——这是天然成立的，不需要任何碰撞检测。

### 4.5 布局常量 layout

`ui/game/board-layout.js:11` 的 `computeLayout(W, H)` 返回一个常量对象，包含：

- 屏幕 `W` / `H`
- 各区域边界：`topH`、`tableTop`、`tableBottom`、`handBottom`、`handMinTop`
- 尺寸：`handW` / `handH`、`tableTileW` / `tableTileH`、各种间距
- 控件坐标：`backBtn`、`buttons`、`restartBtn`、`messageY`

只在场景构造时算一次，之后全局复用。**它不含任何游戏数据，只描述"画多大、画在哪"。**

### 4.6 拖动状态 drag

`ui/game/game-scene.js`

```js
{ id: 't5', from: 'table', x: 200, y: 300, dx: 5, dy: 8, w: 26, h: 36, moved: true }
```

| 字段 | 说明 |
| --- | --- |
| `id` | 正在拖的牌 |
| `from` | 从哪里抓起（`'hand'` / `'table'`） |
| `x` / `y` | 手指当前位置 |
| `dx` / `dy` | 抓起时手指相对牌左上角的偏移（保证拖动时牌不跳） |
| `w` / `h` | 原牌尺寸（拖动时按原尺寸画，避免从桌上抓起时突然变大） |
| `moved` | **是否发生过移动**，用来区分"点击"和"拖动" |

松手后置为 `null`。

### 4.7 数据流

```
createDeck()  造 106 个 tile 对象
     | shuffle
     | deck.pop() x 14 轮   -> 每人 hand（tile 对象）
     | 剩下的                -> pool
     v
玩家拖动（只改 draft：id + 坐标）
     v
点「出牌」
     v
submitMove(index, draft.table.map(g => g.ids))
     | 校验：每组合法 / 桌面牌不多不少 / 至少打出一张 / 首出 >= 30 分
     v 通过
写回 game.table + 从 hand 移除 + endTurn
     v
_syncDraft()  重新从 game 生成草稿
```

### 4.8 关键设计决策

| 决策 | 原因 |
| --- | --- |
| 牌用对象引用而非复制 | 一张牌从手牌到桌面是**同一个对象**在数组间移动，全程只有 106 个 tile 对象 |
| 草稿只存 id | 拖动只关心顺序和位置，不需要复制牌本身 |
| 组的位置存、组内的位置算 | 同时满足"拖到哪放哪"和"绝不重叠"，且免去碰撞检测 |
| 核心层零 wx 依赖 | 可在 Node 下测试、可复用到服务端、可换 UI |
| 场景整块替换而非复用 | 从对局返回模式选择时 `GameScene` 被丢弃，数据自然清空，避免状态残留 |

## 5. 玩法规则实现

### 5.1 牌堆构成

`core/tiles.js:34` `createDeck()`

```js
for (let copy = 0; copy < 2; copy++)        // 2 套
  for (const color of COLORS)               // 4 种颜色
    for (let n = 1; n <= 13; n++)           // 1~13
      deck.push(makeTile(color, n));        // 2 x 4 x 13 = 104
deck.push(makeJoker());                     // + 2 张百搭
deck.push(makeJoker());                     // = 106 张
```

**共 106 张。**

### 5.2 发牌

`core/game.js:38`

```js
const deck = shuffle(createDeck(), rng);                 // 1. 造牌 + 洗牌
for (let round = 0; round < HAND_SIZE; round++) {        // 2. 发 14 轮
  for (const p of this.players) p.hand.push(deck.pop()); //    每轮每人 1 张
}
for (const p of this.players) p.hand = sortHand(p.hand); // 3. 排序
this.pool = deck;                                        // 4. 剩下的就是牌堆
```

- `HAND_SIZE = 14`（`game.js:19`）
- **轮流发**：round 0 给每个玩家各 1 张，round 1 再各 1 张……
- **"发牌"就是从数组尾部 `pop`**，和摸牌是同一个动作
- 洗牌是 Fisher-Yates（`tiles.js:50`），`rng` 可注入以便测试复现

| 人数 | 发出 | 牌堆剩余 |
| --- | --- | --- |
| 2 | 28 | 78 |
| 3 | 42 | 64 |
| 4 | 56 | 50 |

### 5.3 牌组合法性

`core/rules.js`

合法牌组只有两种：

**顺子 run**（`rules.js:22`）：同色、≥ 3 张连续数字，长度 3~13。

算法：先把百搭排除，剩下的必须同色、数字不重复；计算数字跨度与空位，空位必须 ≤ 百搭数；多余的百搭只能接在两端，且不能超出 1~13。

**刻子 group**（`rules.js:52`）：同数字、3~4 张不同颜色。

算法：非百搭部分必须同数字且颜色互不相同。

辅助函数 `realTiles(tiles)`（`rules.js:17`）负责过滤掉百搭，两个判定函数都用它开头。

### 5.4 首次出牌 30 分

`INITIAL_MELD_MIN = 30`（`rules.js:15`）

规则：**该回合打出的所有牌组，非百搭点数之和 ≥ 30**。

点数由 `meldValue()`（`rules.js:74`）计算，它用 `realTiles()` 过滤掉百搭，所以**百搭不计入首出点数**。

### 5.5 两种出牌入口

因为电脑和玩家的操作方式不同，出牌有两个入口：

| | `playMeld(index, tileIds)` | `submitMove(index, tableMelds)` |
| --- | --- | --- |
| 位置 | `game.js:92` | `game.js:141` |
| 调用方 | 电脑 AI | 玩家拖牌 |
| 输入 | 一堆手牌 id（打出一组**全新**的牌组） | 整张桌面的二维 id 数组 |
| 能力 | 只能新增，不能重排 | **可以重排桌面已有牌组** |

`submitMove` 的四道校验（`game.js:141` 起）：

1. 每一组都必须是合法的顺子或刻子
2. 桌面原有的牌一张都不能少（不能把桌上的牌收回手里）
3. 至少要打出自己的一张牌（不能只重排）
4. 未完成首出时，本次从手牌打出的非百搭点数之和 ≥ 30

### 5.6 回合流程

```
await-draw --摸牌--> await-play --出牌/过牌--> (下一位) await-draw
     |                    |
     +--直接出牌----------+   （已允许回合开始就出牌）
```

`turnState` 三个取值：

- `await-draw`：等玩家行动（可以摸牌，也可以直接出牌）
- `await-play`：已经出过牌，仍可继续调整
- `over`：对局结束

回合推进在 `endTurn()`（`game.js:220`）：`this.current = (this.current + 1) % this.playerCount`。

### 5.7 胜利判定

有**两种**胜利方式。

**方式 1：出完手牌**（主要方式）

因为出牌有两条路径，所以判定写了两处，代码完全相同：

- `game.js:121`（`playMeld` 结尾）
- `game.js:209`（`submitMove` 结尾）

```js
if (player.hand.length === 0) {
  this.winner = index;
  this.turnState = 'over';
  this.log.push(`玩家${index} 出完手牌，获胜！`);
}
```

**判定条件只有一句：出牌之后手牌空了。**

**方式 2：牌堆摸空 + 所有人过牌**

`game.js:230`（`endTurn` 结尾）：

```js
if (this.pool.length === 0 && this.consecutivePasses >= this.playerCount) {
  this._settleByLowestHand();
}
```

`_settleByLowestHand()`（`game.js:235`）比较各玩家 `handValue(p.hand)`，**点数最小者获胜**。

### 5.8 计分

`core/tiles.js:61`

```js
function tileValue(tile) {
  return tile.isJoker ? 30 : tile.number;   // 百搭 30 分
}
function handValue(tiles) {
  return tiles.reduce((sum, t) => sum + tileValue(t), 0);
}
```

`getScores()`（`game.js:247`）返回每位玩家的剩余手牌点数，用于结算展示。

## 6. 交互与渲染

### 6.1 触摸事件链路

```
wx.onTouchStart / onTouchMove / onTouchEnd            main.js:31-42
   | pickTouch(e)：优先 e.touches[0]，回落 e.changedTouches[0]
   v
app.onTouchXxx(x, y)                                  app.js
   v
gameScene.onTouchXxx(x, y)                            game-scene.js
```

注意点：

- `onTouchEnd` 时 `e.touches` 是空的，坐标在 `e.changedTouches[0]`，所以必须两者都取。
- 坐标是 CSS 逻辑像素，和 `ctx.scale(dpr, dpr)` 之后的绘制坐标一致。
- `onTouchMove` 每秒触发几十次，里面只做赋值，不做重计算。

### 6.2 手势识别：点击 vs 拖动

点击和拖动共用同一套事件，靠 `drag.moved` 区分：

```
onTouchStart --> 记下 { id, from, x, y, dx, dy, w, h, moved: false }
                    |
       onTouchMove? -+- 有 --> moved = true --> 松手时走【拖动】分支
                    +- 无                --> 松手时走【点击】分支
```

`pickTile()`（`game-input.js:13`）负责"手指按在哪张牌上"：先遍历手牌，再遍历桌面。

### 6.3 拖动落点规则

`_dropTile()`（`game-scene.js`）：

```
松手位置 y 在桌面区域内？
  |- 否 -> 若这张牌原本在桌面，则收回手牌；否则放回原位
  +- 是 -> 计算牌左上角目标坐标 (tx, ty)（夹进桌面边界内）
           先从原位置移除
           findDropGroup(tx, ty) 压到哪一组？
             |- -1（空地）-> addGroup：新建一组，就摆在这里
             +- 第 i 组    -> findInsertIndex(tx) 算插入位置 -> insertToGroup
```

关键函数：

| 函数 | 位置 | 作用 |
| --- | --- | --- |
| `findDropGroup` | `game-input.js:54` | 用"落点矩形"和"组矩形"求交，判断压在哪一组 |
| `groupRect` | `game-input.js:41` | 组的包围盒，`pad = 6` 是吸附余量 |
| `findInsertIndex` | `game-input.js:63` | 落点 x 落在组内第几号位 |
| `addGroup` | `board-draft.js` | 空地新建一组 |
| `insertToGroup` | `board-draft.js` | 插进已有组（**只改 ids 顺序，不动组的 x/y**） |

**"紧紧吸附"是怎么实现的**：插入只改 `group.ids` 的顺序，组的 `x/y` 不动。因为组内坐标是渲染时按顺序算的，所以插进去之后，后面的牌自动往右挪——不需要任何"移动其他牌"的代码。

### 6.4 坐标一致性

这是最容易出 bug 的地方，原则是：**渲染和命中判定必须共用同一套坐标计算**。

```js
// game-renderer.js
const cells = tablePositions({ layout, groups });   // 算坐标
drawTile(ctx, tile, cell.rect.x, ...);

// game-scene.js
const hit = input.pickTile({ ..., tableCells: this._tableCells() });  // 同一个函数
```

两边都调 `board-layout.js` 的 `tablePositions()` / `handPositions()`，所以"看到的位置"和"点中的位置"永远一致。

### 6.5 渲染分层

Canvas 没有 z-index，**后画的盖前面的**。`render()` 的顺序：

```
背景 → 顶栏 → 其他玩家 → 桌面 → 手牌 → 按钮 → 【正在拖的牌】 → 结算浮层
                                            ^ 必须最后画，否则会被盖住
```

同时，桌面和手牌在渲染时会**跳过 `drag.id` 那张牌**，否则会在原位和手指下各画一次。

## 7. 场景与流程

```
HomeScene --点「开始游戏」--> ModeSelectScene --选人数--> GameScene
    ^                              |  ^                    |
    +----------返回----------------+  +--------返回--------+
```

`ui/app.js` 是唯一的路由点：

```js
goHome()               { this.scene = new HomeScene(this); }
goMode()               { this.scene = new ModeSelectScene(this); }
startGame(playerCount) { this.scene = new GameScene(this, playerCount); }
```

**新增场景的步骤**：

1. 在 `js/ui/` 下新建场景文件，实现 `constructor(app)` / `onTouchEnd(x,y)` / `update(dt)` / `render(ctx)`；
2. 在 `app.js` 里加一行 `require` 和一个 `goXxx()`；
3. 场景内部一律通过 `this.app.goXxx()` 切换，**不要直接 require 别的场景**。

每个场景的职责边界：

| 场景 | 职责 |
| --- | --- |
| `HomeScene` | 标题、开始游戏、玩法说明弹层 |
| `ModeSelectScene` | 选人数（2/3/4），把人数传给 `startGame` |
| `GameScene` | 对局：状态、回合驱动、事件分派 |

## 9. 已知限制与后续规划

### 9.1 已知限制

| 限制 | 说明 | 影响 |
| --- | --- | --- |
| 百搭不记录"代表几" | `isRun`/`isGroup` 现算现丢 | 无法在界面上标注百搭替代的数字 |
| 百搭不能挪动替换 | 桌面已有牌组里的百搭无法取回 | 与真实拉密规则有差距 |
| 只能拖单张牌 | 无法整组移动 | 摆牌略繁琐 |
| AI 较弱 | `ai.js` 是贪心算法，且刻子检测有缺陷（`arr.slice(0,4)` 可能取到同色两张） | AI 经常连续多轮出不了牌 |
| 无存档 | 数据只在内存里 | 退出即丢 |

### 9.2 后续规划（按优先级）

1. **百搭挪动与替换**：给 tile 增加 `represents` 字段，实现"用真牌换回百搭"。
2. **修 AI 的刻子检测**：按颜色去重后再取牌（`ai.js:20`）。
3. **整组拖动**：按住组内空白处拖动整组。
4. **新组自动避让**：两组摆重叠时自动推开。
5. **AI 增强**：从贪心换成搜索 / 启发式。
6. **联网对战**：`js/core/` 直接复用到云函数做服务端裁定，客户端只负责渲染与输入。
